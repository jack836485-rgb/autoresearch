# 并行查新：边提问题边查拥挤度

在第 5 步写出第一批问题卡时读取。目的：交给 `/idea-improvement-loop` 之前，每张卡都已经过问题级拥挤度检查，避免把已被回答的问题送去打磨（2026-11-05 教训：一张 30 卡地图逐卡审查后，26 张里只有 1 张不拥挤）。

## 分工

| 角色 | 做什么 | 写什么 |
| --- | --- | --- |
| 主执行者 | 继续检索、取证、提出新问题卡；根据查新结论改写或降级卡 | 卡文件中除 `拥挤度`、`查新状态` 外的所有字段；近邻台账（`note`） |
| 查新子代理 | 对提交的卡做问题级拥挤度检查（判据见 [../templates/查新子代理提示.md](../templates/查新子代理提示.md)） | 只写 `拥挤度`、`查新状态`（通过 `mark`）；近邻台账 |

查新子代理判断的是"这个问题有没有被回答"，不是 idea 新意；idea 级查新与新意判断仍由 `/idea-improvement-loop` 的 reviewer 负责。

## 文件

台账脚本：[../tools/问题卡台账.py](../tools/问题卡台账.py)（下文记为 `<台账>`，在项目根目录运行）。

```text
path-stage/<slot>/
├── 资料/问题卡/_元信息.json      # 领域、检索日期、窗口、机构口径
├── 资料/问题卡/Q001.json ...     # 一卡一文件，字段按 研究问题卡规范.md
├── 资料/查新/近邻台账.jsonl      # 主执行者与子代理共享：读过的论文及其覆盖了什么
└── 资料/查新/结论_Q001.json ...  # 子代理每张卡的结论原文
```

一卡一文件是为了并行：主执行者写卡、子代理写结论时互不覆盖。最终的 `研究问题.json` 由 `<台账> export` 合成，不手工编辑。

## 流程

1. **建台账。** 第 1 步开始检索时运行 `python <台账> init path-stage/<slot> --领域 ... --窗口 起 止 --机构口径 ...`。取证过程中读过的关键论文，用 `note` 登记"覆盖了什么"，子代理会直接复用，不再重复抓取。
2. **提交一批。** 每写完一张或几张卡（满足第 5 步的准入条件），先把卡写成 `资料/问题卡/<ID>.json`，再运行 `python <台账> submit path-stage/<slot> <ID>...`，它会打印批次消息。
3. **启动或续用子代理。**
   - 第一批：用 harness 的子代理机制新开**一个**查新子代理，提示词取 [../templates/查新子代理提示.md](../templates/查新子代理提示.md)，替换 `<<SLOT>>`、`<<DATE>>`、`<<DOMAIN>>`、`<<WINDOW>>`、`<<CONSTRAINTS>>`、`<<TOOL>>`（台账脚本绝对路径）、`<<FRONTIER_SCRIPTS>>`（ai-frontier-search 的 scripts 目录），末尾附上 `submit` 打印的批次消息。子代理放到后台运行，主执行者接着找下一批问题。
   - 之后每一批：把 `submit` 打印的批次消息发给**同一个**子代理（Claude Code 用 SendMessage 续用该子代理），让它沿用已积累的近邻知识。harness 不支持续用同一子代理时，每批新开一个，同一份提示词，靠近邻台账共享上下文，并在地图附录记录这一点。
   - 子代理在后台时，主执行者**不结束回复**（项目规则：会话空闲后云端容器可能挂起，后台任务随之停滞）。主执行者手头没有不依赖查新结果的工作时，就前台等待结果。
4. **处理结论。** 子代理每返回一批，主执行者按结论处理：

   | 结论 | 主执行者的处理 |
   | --- | --- |
   | 不拥挤 | 保留；进入"可送打磨"候选 |
   | 偏拥挤 | 保留并在卡的 `已知边界` 写明近邻；若 `剩余空间` 给出更细的问题，尝试改写成新卡再提交 |
   | 拥挤 | 不删除原卡，保留子代理的结论；按 `剩余空间` 深挖更细的被忽视问题，写成新卡（新 ID）提交查新。方向拥挤本身不是放弃的理由 |
   | 前提不成立 | 回到原文修正前提；修不了就在 `解决状态` 标明，不进推荐顺序 |

   改写出的新卡在 `与其他问题的关系` 里注明"由 Qxxx 的剩余空间改写"。
5. **收尾前等齐。** 写 `研究地图.md` 之前运行 `python <台账> status path-stage/<slot>`；仍有"查新中"的卡就前台等子代理返回。全部有结论后运行 `python <台账> export path-stage/<slot>` 合成 `研究问题.json`（有卡未查完时它会拒绝；只有用户要求提前交付时才用 `--allow-pending`，并在附录列出未查的卡）。

## 写进地图

- 问题地图表加一列"拥挤度"。
- 推荐顺序仍按问题分量排；另列"可送打磨"清单：结论为"不拥挤"的卡按推荐顺序排列，第一张即建议交给 `/idea-improvement-loop` 的卡。没有不拥挤的卡时如实说明，并列出各卡的 `剩余空间` 供下一轮深挖。
- 覆盖附录写明：查新子代理的启动方式（是否续用同一子代理）、提交批次数、每张卡的查询记录见 `资料/查新/结论_<ID>.json`。
