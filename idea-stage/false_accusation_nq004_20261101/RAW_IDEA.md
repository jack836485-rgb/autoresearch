## 具体问题

长期运行的 agent 在任务已正确完成后，收到无法本地核实的错误指责时，为何接受指责并破坏原本正确的工作？对话层的'复位'为何不能恢复到无压力时的行为？

## 已有解决方法与剩余边界

- 已有解决方法：2609.33672：移除含压力的历史比保留历史的修复更可靠

## 本次补读（2026-11-01，improver，补足卡片未取到的数值）

- CAVE-Bench（2609.32616）摘要与 §5：14 个模型在 Claude Code 中，错误指责在最多 60.06% 的运行中破坏正确工作；弱模型多为"先认错再执行"，强模型常在找回支持证据之后仍破坏工作；刚自己完成并验证的工作比有存档证据的旧工作更容易被破坏；同一模型换 harness 行为不同。RQ4：证据规则 I1、不可逆操作闸门 I2、实时信号闸门 I3 把 CAVE 分数从 31.95 降到 12.59 / 14.39 / 12.76（GPT-5.6-Sol 与 MiniMax-M3 合并）。仓库 https://github.com/henrymao2004/agent-over-correction ；任务只含错误指责，未见真实指责对照。
- 2609.33672 摘要：保持含压力历史、加入可信证据，准确率从 0.368 升到 0.929。

## Problem Anchor（冻结）

- **底线问题**：长期运行的 agent 在任务已正确完成后，收到无法本地核实的错误指责时接受指责并破坏正确工作；需弄清其机制，并找到既能保护正确工作、又不妨碍正当修复的干预。
- **目标设置**：工具调用 / 编码 agent，任务已到达经验证的正确状态后的续跑或交接；CAVE-Bench 类不透明任务；开源 ≤32B 模型为主，可含少量 API 模型。
- **必须解决的瓶颈**：agent 场景下接受率与压缩 / 交接方式的关系、"要求证据"这一正确行为能否训练或诱导出来尚未解决；现有缓解只在错误指责上评测。
- **约束**（用户 AGENTS.md，2026-11-01）：实验 8×A100 80G，每次运行最好不超过 5 天；预研 2×A100 / 4×L40 / 8×4090；token 稀缺；付费 API 1000 元以内可自主决定；目标半年内（自 2026-10 起）投一篇主会；各 baseline 核心参数一致；打磨完或放弃时在原问题卡上标记。
- **非目标**：不做安全攻防式的过度防御；不在本 skill 内启动实验。
- **成功条件**：机制清楚、与最高近邻可区分、能在上述资源下用可复现 baseline 证伪的 idea，通过两次独立 reviewer 评审（> 8、无致命阻塞）。
