## 背景

**定位关键词：** API tools；pagination；interactive coding agents

**一句话定位：** 分页API的工具agent如何区分一个见证已足够与必须枚举完整集合的任务。

## 核心 Claim

AppWorld支持分页，Agents Don’t Paginate报告实际agent很少请求第二chunk；尚需诊断AppWorld中局部结果被当全局结论的失败。主张分页停止不能用统一“有证据/翻完页”规则：存在性命题找到一项即可，否定存在性和精确计数则必须有枚举完整证据。查询语义决定证据要求，才能在同预算减少过早停止与无效翻页。

分页遗漏有外部经验事实，AppWorld具体因果失败待验证；被忽视关键是正存在与全局否定的观察需求不对称；迁移数据库中见证和集合完备性的逻辑，生成查询专属停止条件；两类任务出现相反的预算收益交互才支持机制。

## 方法设计的核心思想

同一actor根据用户原始要求和公开API文档，在正常生成调用的轮次输出一个窄查询类型：存在/不存在、所有对象、精确计数；其他不识别类型沿用原agent。CPU为该查询记录相同参数范围内已读页/游标、目标见证和公开结束信号：存在命题有合法见证可结束，否定存在或计数未枚举完整则只返回“尚未知/部分计数”并让原actor继续。对“所有对象满足”的正结论需完整，对反例只需一项。首版限静态集合/只读查询；不读数据库和评价答案，不自动调用某个硬编码API。

## 最小实验

AppWorld train/dev按公开任务文本和文档预先固定存在/否定/计数三类任务；独立人工标注语义类型与轨迹已查范围，不能用本方法自分组。原分布正式TGC与诊断对分开报告；对同一文档支持场景交换查询语义的成对诊断，仅改变存在/计数要求，不能只选失败例。对照官方ReAct、普通分页提醒、固定多读一页、统一全枚举覆盖门、本方法；统一模型、工具和完整token预算。支持条件是计数/否定组少过早停止，存在组比全枚举少调用，且超过普通提醒；若类型不可靠或只有多读收益则否定。

同一actor快照、任务ID/公开查询语义分组、文档、起始环境、提示内示例、temperature/seed、最大token/LLM调用/公开API调用。语义类型提取计入同一轮输出与总预算；只追踪已有公开工具返回。所有新增标准对照在下表完整规范，本轮不执行。方案参数在实验计划阶段与用户定。
