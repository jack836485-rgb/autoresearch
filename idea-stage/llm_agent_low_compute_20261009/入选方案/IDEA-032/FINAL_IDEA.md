## Title

# 批量操作中的分页覆盖失效：由agent自身写操作触发范围重开

**候选ID：** IDEA-032。**独立审查：** Call24，7.7/10，experiment_ready，无致命阻塞。尚无模型实验结果。

**定位关键词：** API tools；pagination；stateful execution。

**一句话背景：** 交互式代码agent在分页读取同时修改结果对象时，怎样避免每次API都成功而最终漏处理一部分目标。

**独立创新点：** 从公开文档和agent生成代码识别自身对同一分页集合的写入，让已扫描范围随这些实际写操作失效；标准数据库分页和恢复策略本身不是新贡献。

## 1. 引言式概述

### 1.1 任务锚点与最小范围

研究AppWorld中按条件批量删除／修改对象的任务。初版只涉及agent自己的写操作，不加入其他用户并发写、罕见竞态、真实支付或安全攻防。工具通过API actor调用，环境和代码分析在CPU运行，无需训练模型。

需要解决的瓶颈是“正在枚举的集合已经被自己改动，却继续相信旧的页边界”。这比一般提醒“不要忘记翻页”更具体。

### 1.2 现有方法怎样处理

[AppWorld](https://arxiv.org/abs/2407.18901)公开页号分页、状态写入及代码agent。[官方ReAct提示](https://github.com/StonyBrookNLP/appworld/blob/main/experiments/prompts/react_code_agent/instructions.txt)已经要求处理所有page_index，因此不能把给它加同一句提醒当独立方法。

[ACE](https://arxiv.org/abs/2510.04618)从执行反馈积累分页操作知识。[HyperAgent](https://arxiv.org/abs/2608.02650)从工具schema规划依赖；[TraceCompiler](https://arxiv.org/abs/2608.02680)从轨迹恢复依赖和分页循环。它们给出重要近邻，但目前检索没有直接看到agent自身写入使分页覆盖失效的实证和控制闭环。

### 1.3 具体失败与证据边界

页号／offset枚举在删除后跳项是经典问题，[Zendesk官方说明](https://developer.zendesk.com/documentation/api-basics/pagination/paginating-through-lists-using-offset-pagination/)也解释了这种机制。假如第一页是A、B，后面是C、D；删除A、B后，C、D会前移。直接请求旧的第二页可能返回空，agent便误以为已经处理完。

AppWorld支持这一组合，说明失败可达；尚未证明自然任务中出现得足够频繁，也没有误漏比例。研究必须先诊断，而不能用一个人工例子冒充普遍效应。

### 1.4 我们实际做什么

我们给正在扫描的查询维护范围状态。原actor从公开文档标出读取集合及写操作影响，CPU根据生成代码的数据流和实际成功写回执，判断写入是否影响同一集合的成员、筛选字段或排序字段。影响发生后，原有“这些页已经覆盖”的结论被撤销，actor需要重新规划剩余范围。

可选恢复动作仅有已有标准策略：先收集ID再写、文档确实提供时使用稳定cursor、或重新查当前前缀。它们不是发明。新意是何时由实际自身写入触发范围重开，以及这个判断是否有价值。

### 1.5 最小实验概览

相同AppWorld任务、模型、接口和完整预算下，先统计自然扫描—写入—继续翻页轨迹，再比较官方ReAct、FullCode、先收集后执行、显式范围重开。所有组得到同样的可见调用记录；先收集ID这个便宜强对照已经解决时，应停止复杂机制。

### 1.6 拟验证贡献

1. 对自身集合修改引起的silent omission做独立诊断，区分它与普通未翻页、读错条件和工具报错。
2. 以可见同集合写入为触发条件，更新agent的分页覆盖状态。
3. 同预算比较动态范围重开与便宜标准策略，确定是否存在额外收益。

## 2. 详细方法计划

### 2.1 方法直觉

读过某一页只证明读过当时那个集合的位置；自己改变集合后，旧位置不能继续作为覆盖证明。

1. 原actor根据当前公开文档和用户条件，标明分页查询、筛选／排序和相关写目标。该解释输出计费，不能免费给人工完美标签。
2. CPU分析实际生成代码中的API调用和返回对象ID的流向，维护查询范围和已处理ID，不保存隐藏数据库内容。
3. 实际成功写回执与已读对象相连时，结合文档影响判断它是否改变正在枚举的集合。
4. 确认影响后，将旧分页范围标为失效，并向下一次规划提供剩余目标和已处理ID；原actor选标准恢复策略。
5. 无法判断影响时保留“范围未验证”，由原actor查询或改计划，不能悄悄将未知写入当成确定无影响。

### 2.2 输入、输出与成立条件

输入是任务条件、公开API文档、agent代码、可见API参数和返回、页号及已处理对象ID。输出是某个查询范围是否因自身写入失效，以及应重新规划的剩余范围。

首版假设集合变化仅来自当前agent，API文档能说明至少一部分写影响。没有稳定cursor的API不能凭空获得cursor。某个写入改变其他集合，不应让所有扫描重来；未改变筛选／排序的属性写也不应自动使覆盖失效。

### 2.3 算法与数据流

范围记录采用可读查询描述、参数、排序、已见页和已处理ID；不加哈希或指纹。不同查询参数和排序对应不同范围，不把相似查询强行合并。

CPU的最小判断是：实际写对象来自正在扫描的结果，且公开写语义会删除成员、改变筛选成员资格或改变排序位置。满足时撤销该范围后续页边界的有效性；写只是修改不相关属性时继续保留。

覆盖状态更新是确定性的，API语义解释仍可能错，因此不能把它自身当评价真值。初版使用Python AST支持的直接API调用与简单循环；复杂动态代码的覆盖率要另报，任务失败仍留在总分母。

先收集后执行对照会完整枚举ID，然后逐项写；重新查前缀策略需记录已经处理的ID，防止修改不移出筛选集合时反复处理。状态改变不保证一次重查就足够，仍要按任务条件判断剩余对象。

### 2.4 最小实现与算力

[官方仓库](https://github.com/StonyBrookNLP/appworld)的ReAct、FullCode、environment.py和pagination.py已直接读过。页号分页是真实实现，环境为持久Python shell；原模型调用可使用API。

新增CPU AST/范围侧表和调用边界记录。记录限agent本来调用的参数与公开返回，各组共用；读取数据库、评测代码、gold solution或task completion oracle不允许进入controller。初始执行、所有读取／写入、失败重试、解释输出和状态序列化均计入总预算。本轮仅源码核验，未安装或实跑。

## 3. 最小验证实验

### 3.1 目的

先确认自然bulk-action任务中是否真的有自致分页漏项，再看机制能否超过简单收集ID。未发现足够失败，应结束这个方向。

### 3.2 数据与评测设置

从AppWorld train/dev筛选存在分页与同集合写入的任务，筛选依据公开任务/API结构，不能按主方法成功与否筛选。用dev冻结影响解释规则，再评价held-out任务；公布筛选覆盖率以及全集成功率。

另外构造同一个真实失败前缀的配对继续执行，评测器可复制模拟世界以保证起点相同；复制状态不能交给agent。配对诊断与自然end-to-end结果分开，不把人工强制边读边删当自然频率。

### 3.3 Baselines（唯一实验baseline定义）

| Baseline | 同任务依据 | 代码核验／本地完整规范 | 复现路线 |
|---|---|---|---|
| 官方ReAct | AppWorld原任务基础agent | 已读SimplifiedReActCodeAgent；原提示已包含全页提醒 | `appworld run auto --agent-name simplified_react_code_agent --model-name {共同actor} --dataset-name dev` |
| 官方FullCode | 同任务整段程序及错误修复 | 已读SimplifiedFullCodeAgent和真实持久环境 | 同入口，agent-name换为simplified_full_code_agent；统一API/token预算，批量调用不能免费 |
| 先收集ID再执行 | 标准且强的枚举后修改策略 | 相同查询循环先枚举全部目标ID并保存，结束枚举后逐ID写；不用隐藏快照 | 同ReAct/观察口本地CPU策略，枚举与写的全部费用计入 |
| 写后重查当前前缀 | 更便宜的动态修正策略 | 每次会改变筛选成员资格的成功写后从当前第一页重查；保存已处理ID，避免重复 | 同支持任务和影响说明，不能给主方法额外准确影响标签 |
| 本方法范围重开 | 待验证机制 | CPU按实际同集合读写影响使覆盖失效，actor选择标准策略 | 同原agent接口；仅新增范围状态更新，不更换模型 |

通用“处理所有分页”提醒并入官方ReAct，不另列重复实验臂。ACE是重要同任务近邻，其AppWorld公开fork此前已核验；可在最小诊断通过后加入完整原生流程比较，reflector/playbook构建成本不得免费。HyperAgent未核验公开实现、ASSAY当次代码不可访问，不冒充可运行baseline。

每个比较内部固定模型快照、任务顺序、API文档、few-shot、温度、最大上下文／输出、工具与LLM总调用、总token和seed。不得只按外层代码cell数控制预算而让一组无限批量API。金额、任务数和重复seed在实际实验前与用户确定。

### 3.4 指标

主指标是自然任务成功率及漏处理的实际目标对象比例。诊断记录API全部成功但目标残留的轨迹、写前后页边界变动、错误失效和漏失效。独立标注使用公开代码/轨迹及仅评价使用的环境真值，不能把controller的状态当ground truth。

同时报告完整token、API/LLM调用、CPU分析时间、重复对象操作、无谓重新扫描和目标条件变化。只降低漏项却显著增加整体失败，不能称有益。

### 3.5 支持和失败条件

需要发现真实自致遗漏、范围检测有合理准确性，并在同预算比便宜对照改善完成率或完整成本。若先收集ID等效、自然任务没有这类问题、影响解释不可靠、或重查造成循环，则停止复杂方法。无独立算法新理论可主张。

## 4. 后续实验计划

1. 分删除、改变筛选字段、仅修改不相关字段，检验何时必须使覆盖失效。
2. 消融同集合识别、实际写回执和已处理ID记录，确认收益来源。
3. 同模型内部改变页大小和预算，并在不同actor重复，不混淆模型变化。
4. 加入同任务ACE完整流程，比较固定分页技能与运行时变化处理。
5. 展示自然漏项和错误重开两类轨迹；必须报全集覆盖与成本。

## 5. 风险与开放问题

真正的新意偏经验性，取决于自然失败规模；数据库恢复策略都是已有方法。文档影响解释可能错，复杂代码未必能分析，某些标准对照也可能已经足够。首个诊断需同时观察自然失败、影响识别和强便宜对照，不能等大规模跑完才承认不存在研究问题。

独立reviewer通过的是可进入实验规划的门槛，不是效果证明。需要先验证这条研究问题是否值得做，再决定投入API预算。
