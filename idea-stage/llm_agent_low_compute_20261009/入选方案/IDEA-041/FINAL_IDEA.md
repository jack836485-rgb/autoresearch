## Title

# 失败代码的修复以已提交效果为边界做剩余程序求值

**候选ID：** IDEA-041。**独立审查：** Call25，7.8/10，experiment_ready，无致命阻塞。未运行模型实验。

**定位关键词：** interactive coding agents；stateful execution；execution feedback。

**一句话背景：** 交互式代码agent在一段程序部分写入后报错时，怎样修复后续计算而不重新执行已完成的效果。

**独立创新点：** 在agent生成的部分执行代码中，将外部已提交效果与可重算的纯数据依赖分开，求可继续的剩余程序。

## 1. 引言式概述

### 1.1 任务锚点与最小范围

限定AppWorld中部分写入后抛错的单个Python代码块。首版支持顶层顺序赋值、直接API调用和固定列表简单循环，不支持任意Python、嵌套异步或不确定timeout。新增机制CPU运行，actor使用统一API，不训练模型。

### 1.2 现有方法怎样处理

[AppWorld](https://arxiv.org/abs/2407.18901)的FullCode将stack trace交回模型再生代码。持久user_ns使普通顶层赋值可能已经保留，因此不能声称报错总会丢变量。Temporal已有历史Activity结果回放；Kishu已有notebook依赖恢复；DART/AgentRewind已有恢复边界。它们分别覆盖重要原理，本文差别仅是模型修改后的单个cell内部调用实例与剩余纯依赖。

### 1.3 具体瓶颈与证据边界

代码报错不回滚先前写入。需要先诊断更窄失败：原actor避免重复写时丢掉返回对象ID，或循环/未完成赋值中可用的依赖值不再可取得，剩余任务仍失败。该路径可达，但发生率尚未观察。已保留的普通变量是反例边界，不应强行重新恢复。

### 1.4 我们实际做什么

我们把已成功写调用替换成其公开返回，并根据实际失败点重算剩余所需的纯表达式，保持外部效果与其数据依赖。CPU对齐源码位置、循环实例和实际实参；新参数的合法新写不被当成旧效果。修复已完成效果需要原actor显式补偿/换计划，而不是默默重新执行。

### 1.5 最小实验概览

同自然失败前缀、可见记录和预算比较FullCode、强remaining-code提示、成功回执去重、无依赖保留和剩余求值。只有超越回执去重和强提示，且真实自然任务有相应失败，才说明程序残余化值得做。

### 1.6 拟验证贡献

1. 实例级效果与返回值的剩余执行边界。
2. 区分普通已保留变量与真正丢失/覆盖依赖的自然失败诊断。
3. 配对恢复与端到端预算对照，验证新增CPU机制的必要性。

## 2. 详细方法计划

### 2.1 方法直觉

已经发生的外部效果保留，后续真正需要的计算继续。

1. CPU为支持的AST添加可见调用观测；记录位置、循环实例、参数、返回及成功状态。
2. 失败后保留有明确成功回执的写入。
3. 原actor只修失败调用与未执行后缀。
4. CPU把已完成写替换为返回常量/已有对象引用，并重算必要纯依赖。
5. 重复到达既有写实例时复用结果；未知效果不套用这一保证。

### 2.2 输入、输出与成立条件

输入：自己生成代码、公开API参数/返回、实际失败点和已有可见变量。输出：一段保持已知效果的剩余代码及无法支持的情况。需要调用实例可对齐、纯表达式确实不触发额外I/O、返回值可安全作为原类型值使用；不能仅靠源码文本位置在大幅重排后错误对齐。

### 2.3 算法与数据流

用AST和实际调用轨迹构建数据依赖闭包。对每个成功写保留原返回，修复后相同位置/循环实例/实参才能复用；不加哈希或指纹。纯计算依赖由已知返回向失败点和后缀传播，只重算必要节点。初版禁止把动态eval或隐式I/O函数标为纯；不支持则交原actor正常恢复并记入总体失败/成本。

这不是通用确定性replay：修复模型可能改变程序，因此必须验证调用实例对应。若原代码完成了错误写，本方法只保留“已做过”的事实，不把它提升为“对任务正确”。

### 2.4 最小实现与算力

已读[官方FullCode/environment](https://github.com/StonyBrookNLP/appworld)：_shell_run_cell、execute及user_ns真实存在。需要新实现AST观测、实例匹配和纯依赖残余化。只记录agent自己的可见调用，不能读task数据库/gold。环境和AST计算CPU；所有修复、额外输入输出、调用、初始失败均计费。源码核验不是实跑。

## 3. 最小验证实验

### 3.1 目的

先验证“回执去重后仍丢依赖”的失败是否存在，再验证残余计算是否解决这个独立问题。不能只减少重复写就宣布成功。

### 3.2 数据与切分

自然AppWorld train/dev失败轨迹做独立诊断，dev冻结支持语法及实例对齐。评测器复制同一失败前缀后的模拟世界做配对继续，但复制内容不提供controller；另报自然held-out端到端结果。各组同起点、同模型、相同文档/few-shot/温度/seed及完整API/LLM/token cap。

### 3.3 Baselines（唯一实验baseline定义）

| Baseline | 与定位关键词及目标任务的关系 | 论文或规范 | 开源代码与核验结果 | 具体复现方式 | 是否纳入最小实验 |
|---|---|---|---|---|---|
| 官方FullCodeRefl | 同AppWorld代码执行与错误恢复 | https://arxiv.org/abs/2407.18901 | https://github.com/StonyBrookNLP/appworld；full_code_agent.py、environment.py与README已读 | appworld run auto --agent-name simplified_full_code_agent --model-name {共同actor} --dataset-name dev；所有组同task/seed/API与token cap | 是；未实跑 |
| 强remaining-code提示 | 排除仅把部分执行事实说清楚 | 本地标准对照规范 | 同FullCode；加入成功效果、返回值、失败行并明确不得无意重跑已完成操作 | 与主方法同观测表；actor自由生成剩余code，不做CPU残余变换 | 是 |
| 成功回执去重 | 一般避免重复写的强简单策略 | 本地标准对照规范；VTC仅作原理近邻 | 按执行实例的源码位置/循环索引/已知实际参数直接比较，若已成功写则重用原返回；不求纯表达式依赖闭包 | 同仪表记录、task/actor和预算，不使用幂等键或环境私有数据库 | 是 |
| 无数据依赖的剩余后缀 | 检验返回值/局部依赖保持的独立作用 | 本地机制消融 | 在失败点继续修复，已提交写禁止重跑，但不替换已完成调用为返回表达式 | 同支持语法与执行记录；无效局部变量错误照实计入失败 | 是 |


所有组共用调用边界记录；无免费完美标签、初始执行或额外修复轮。批量代码内部API逐次计费。Sentry当前完整代码未发布，DART公开语义恢复对齐存在疑问，Temporal/Kishu不属同一任务，均只列近邻而不当已核验AppWorld baseline。

### 3.4 指标

主指标是剩余任务及最终task成功、重复写和因依赖缺失产生的失败；次指标API/LLM/token、CPU实例匹配时间、支持语法覆盖、误匹配/错误复用。所有不支持或超时轨迹留在总体分母。评测器状态只用于评分，不能输入actor。

### 3.5 支持和失败条件

真实失败入口非零、效果和依赖恢复正确、比强提示/回执去重改善同预算完成才支持。变量通常已保留、纯依赖成本抵消收益、只在人工特殊代码有效、或修复重排导致错误调用复用时停止。

## 4. 后续实验计划

1. 拓展简单循环与多个失败点，先验证每种语法再扩大Claim。
2. 消融返回替换、纯依赖重算和实例对齐。
3. 分析自然变量保留与丢失/覆盖两类轨迹。
4. 不同actor/预算下重复，同设置内参数公平。
5. 展示误匹配失败和有效剩余程序案例。

## 5. 风险与开放问题

自然失败规模可能很小，因为IPython已有持久变量。模型修改代码后的调用对齐是主要实现风险；未确认映射不能跳过效果。成功回执不证明该写任务正确，不确定timeout也不能纳入已提交保证。最终方案不能扩大成任意Python持久工作流恢复。
