## 摘要

过去半年，"上下文压缩"在 agent 里已经从推理加速技巧变成训练和产品默认组件（CompactionRL、Memento、Cursor Composer 自摘要、Claude Code /compact）。证据最集中的几个观察：

1. **带压缩训练的增益来源没被拆开。** CompactionRL 在 106B 上的 7.0 分增益里，"不训练 summary"的消融就拿到了 4.7 分；30B 模型训练后，压缩模式变好，单窗口模式却从 47.5 降到 43.7。Memento 发现：没有 SFT 冷启动时，RL 会在 20 步内放弃压缩工具。
2. **压缩发生在未来需求未知时。** 多个独立设置都显示，按当前问题选出的保留内容，对之后才出现的问题几乎不比随机删除好；保留决定了任何检索器的上限。
3. **单轮保真度不预测多步成功。** ICAE 在 SWE-bench 上 BLEU 高于基座，解决数却少 12 题；冻结读者只能读接近自己写出的 KV，几何上相近也没用。
4. **何时压缩的可预测性有限。** 590 个真实 AppWorld 压缩边界上，最佳历史特征触发器 AUROC 0.66，同一边界两次重放之间也只有 0.72。
5. **摘要会写入压缩器自己的推理并抹掉来源。** 开放待办 67.7% 没有环境来源。这类诊断在窗口内至少有 8 篇，非常拥挤。
6. **成功率与 token 数不衡量真实代价。** benchmark 环境允许重读文件，掩盖了损失；改写历史会打断前缀缓存，token 减少 38% 而计费上升 7%。
7. **KV 级与文本级压缩没在同一 agent 预算下比较过**（反证检索未检出）。

## 按问题展开

### Q001 带压缩训练学到的是什么

> **打磨记录（2026-11-04）：** 已用 idea-improvement-loop 打磨，2 次审查未过（最好 5.5/10），用户决定停止。"给 summary 新增专属信用估计器"路线已饱和（另见 HiMPO 2606.16285、TreeMem 2605.04811、DSSR 2609.32805）；本卡三个子问题仍未回答。详见 `idea-stage/compaction_rl_attribution_q001_20261104/PIVOT_OR_STOP.md`。

**对象与失败条件。** 窗口内 agent 训练开始把 compaction 放进 rollout：CompactionRL [1] 联合训练执行与 summary；Memento [2] 用 note 替换历史；AutoCompact [7]、ContextPilot [8]、ReSum [9] 学习压缩动作；AdaCoM [3] 冻结执行 agent，只训练外部管理器。

**实验发现。**
- CompactionRL [1]（Tsinghua；GLM-4.7-Flash 30B / GLM-4.5-Air 106B；SWE-bench Verified 随机 200 题 + Terminal-Bench 2.0；单次运行）。106B 在压缩模式下 SWE：基座 59.8 → 不带压缩的 RL 62.5 → 带压缩但不训练 summary 64.5 → 完整 66.8。也就是说，7.0 分增益中约 2.7 分是一般 RL，约 2.0 分来自"执行器在压缩下训练"，只有约 2.3 分来自 summary 本身被训练（本地图按表粗分，未估方差）。30B 上，完整 CompactionRL 让压缩模式 SWE 从 50.5 升到 56.0，但单窗口从 47.5 降到 43.7、长窗口从 53.5 降到 49.0（列含义按表头 Single/Comp/Long 顺序解读，本轮未逐一核对表注）。
- Memento [2]（Columbia；Qwen3-8B）：SFT+RL 比仅 SFT 高 23.9 分、比仅 RL 高 8.8 分。没有 SFT 初始化时，RL 在 20 步内把压缩率压到接近 0，并一直保持；RL 开始时两种初始化的准确率几乎相同，差别只在压缩频率（4 倍以上）。
- AdaCoM [3]（Alibaba Tongyi；BrowseComp-Plus）：给 DeepSeek/Kimi/Qwen/GLM 学到的管理后上下文长度分别约 1.9K/3.4K/5.2K/7.0K，与各自 ReAct 原生表现排序一致。较弱 agent 被学成"每轮都压"，较强 agent 被学成"保留原始工具结果"。
- MemoryWalker [4]（Alibaba）形式化指出：每次驱逐都让历史分叉，训练对象是树。沿最终压缩路径训练会产生 time-travel leakage，回放全历史则造成训练-推理不一致。ECHO [5] 指出压缩后的上下文丢掉了证据来源，结果奖励无法把信用分配给真正起作用的观察。KV-streams [6] 处理的是重复 prefill 带来的训练吞吐问题。

**解释与处理。** 已支持：训练对象分叉（[4] 的形式分析）、最佳压缩强度依赖执行 agent（[3]，相关性证据）。待验证：Memento 作者认为 RL 采样不到执行良好的压缩轨迹，所以学会回避工具；本地图推断 CompactionRL 的增益相当部分来自执行器适应有损 summary，且模型可能变得依赖压缩。

**分歧与缺口。** 没有工作把"summary 变好"和"执行器更能容忍差 summary"分开，例如交换训练前后的 summarizer 与 actor 做 2×2 配对。RL 回避压缩的原因（短期奖励惩罚、长度项、信用无法回传到压缩动作）也没有经过干预区分。带压缩训练损害单窗口能力，只有单模型单次的观察。

**下游切口。** 固定任务与预算，交换训练前/后的 summarizer 与执行器形成配对，看增益来自哪一边；记录 RL 过程中压缩动作的优势估计与频率；在单窗口/长窗口模式下复测训练后能力，控制 RL 步数与数据。

### Q002 查询未知时保留什么

**对象与失败条件。** 无论文本 compaction 还是 KV 驱逐，写入/驱逐都发生在未来问题出现之前。很多方法的评测却让压缩器看见查询，或用近期注意力当作未来注意力的代理。

**实验发现。**
- [10]（Stanford；合成流式回忆，300 个 episode，保留×选择全交叉）：固定访问权限时，查询感知选择提升 15.5 个百分点（95% CI 12.8–18.2）；而混合比较报告的 68.7 点优势中，53.2 点来自访问权限差异。有界保留下，所有选择器（包括 oracle）都被保留率封顶，例如 recency 保留行约 46.8%。作者强调饱和是生成器性质，"上限"才是一般结论。
- EMBER [11]（NVIDIA；LongMemEval-RR）把 Retain-Recall 与 Read-Recall 分开度量，在 B_ret=8192 下 EMBER-14B F1 0.3017。
- AgentKV [12]（Imperial/Columbia）：think/act/tool 等阶段的 query 子空间主角度明显大于同阶段内部，所以用最近 token 当代表 query 会系统性低估后续阶段要用的 key。
- [13]（Yonsei；确定性基准）：与查询弱对齐的上游前提块在预算压力下被驱逐，依赖感知规则把全链保留率从 0.03 提到 0.90。
- 【外】[14]：25% 预算下，为已知问题选句，open-decider 得 70%（随机删除 61%，全文 74%），gpt-6-luna 得 77%（67%，89%）；对之后的隐藏问题，没有方法可检测地优于随机删除。
- 【外】[15]（Qwen3.5-4B/27B，在线 KV compaction）：proxy query 的选择最关键；延迟一轮、等未来生成的 query 出现再压缩，效果更好。

**解释与处理。** 已支持：保留决定检索上限（[10] 的算术论证与实验）；近期注意力不是未来注意力的好代理（[12]）。已有处理：学习式保留（EMBER）、阶段/生命周期/步级 KV 打分（AgentKV、CommitKV [45]、StepKV [46]、IntentKV [47]）、依赖图规则（[13]）、延迟压缩（[15]）。

**分歧与缺口。** 写入时可得的哪些状态特征（任务依赖、阶段、未完成子目标）能预测未来使用，以及这种预测力的上限多高，没有统一度量。强证据多来自合成或阅读理解场景，工具交互 agent 上的直接证据少。文本线和 KV 线各自只和同层方法比较（见 Q007）。

**下游切口。** 在真实 agent 轨迹上，用重放或恢复反事实标注每段内容之后是否被用到；比较不同写入时信号对未来使用的预测力，与同预算随机保留对照，文本级与 KV 级分开报告。

### Q003 潜在/KV 形式的压缩为何在多步 agent 中失效

**实验发现。**
- [16]（TUM；Qwen3-8B，ICAE 4× 压缩）：SQuAD/RepoQA 上 ICAE 高于基座、低于 SFT。在 SWE-bench Verified 上，BLEU_ref 同样高于基座，但解决数比基座少 12（p=0.013；基座 19、SFT 86）。定性分析看到重建时 URL、文件路径被幻觉替换。由于解码器未训练，作者把问题归于压缩机制，并提出"误差累积"与"长程依赖丢失"两个假设，但没有做区分实验。
- [17]（MIT/IBM）：冻结读者只能读取接近自己会写出的 cache（tolerable set）。几何相似度不预测可用性，失败也不是渐进的；只从发送方一侧构造替换的方法被限制在底线附近，提高保真度也无帮助。追加 cache 并只适配 query 侧的方式不受此限。
- Remory [18]（Alibaba/CUHK，摘要级）：在文本 summary 后追加残差软 token，改善来源归因。[19]（AWS，摘要级）：prompt 区上层 KV 的冗余是"聊天模板形式"而非内容。

**缺口。** 多步 agent 中隐式压缩失败的机制没有受控区分；单轮保真指标为何不能预测多步成功，没有系统测量。本地图推断：agent 任务依赖路径、ID 这类低冗余的精确标识符，连续表示对它们的保真度可能远低于平均水平，这一点待验证。

**下游切口。** 在同一压缩器下，分别测精确标识符与一般内容的重建保真度；在多步任务中逐步注入/移除压缩段，看失败是随步数累积，还是集中在需要回溯早期标识符的步骤；控制压缩率与读者是否训练。

### Q004 何时压缩：伤害有多可预测

**实验发现。**
- [20]（Salesforce；TRACE 语料 590 个 AppWorld 压缩边界，每个边界分别用压缩前上下文和 summary 从同一前缀状态重放）：344 个边界有正负担（后续报错或重复调用）。最佳 boosted 分类器的留出 AUROC 为 0.66 [0.61, 0.70]；80% 保留时挡住 24.7% 的正负担边界，随机期望是 20.0%。logistic 规则按负担质量计算没有优势。同一边界两半重放互相预测的 AUROC 为 0.69–0.72，半-半相关 0.40，符号一致 κ 0.28。
- SelfCompact [21]（JHU/Apple）：固定间隔摘要会在子目标中途抹掉已验证事实；由模型按 rubric 决定何时压缩，在搜索任务上每题 token 成本比不压缩低 30–70%，在数学上 12 个单元中领先 11 个（匹配 token 预算）。StateComp [22]、AutoCompact [7]、ICLR [23]（WorkBuddyBench 260 题，平均奖励 0.699→0.718）都主张学习时机或可遗忘内容。

**分歧与缺口。** 学习式触发方法通常和固定阈值比，没有和"同保留比例的随机时机"比，也没有报告自己相对重放噪声上限处于什么位置。[20] 的结果说明，单靠行为历史的触发器，上限被续写随机性约束住；可预测部分究竟来自轨迹结构还是 summary 质量，还没分开。

**下游切口。** 在配对重放语料上，以同保留比例的随机时机为基线评估学习式触发器；把边界伤害分解为"可由状态预测"与"续写方差"两部分；固定 summarizer。

### Q005 摘要混入无来源推理、抹掉约束与权限

**实验发现。**
- 【外】SJC [24]（OpenClaw 压缩器，AppWorld 90 任务 ×3 次）：667 个 summary 的 26,881 条中 17.9% 无来源。按分节看，精确标识符 3.4%、约束 11.1%、决策 21.0%、开放待办 67.7%、待处理用户请求 86.1%。推理类条目在首个边界有 54.9% 无来源，而且每个 summary 都重新写入约 4 条，不是从上一份继承。摘要称 83% 失败运行可追溯到执行某条 summary 条目的动作。比例由保守 judge 判出，是上界。
- AuthMem [25]（Tsinghua）：记忆整合后的越权（Upgrade-all）从 GPT-5.5 的 5.2% 到 Gemini 3.1 Pro 的 30.4%。但低越权率部分来自省略：H- 案例中 74.0% 被直接省略。来源感知提示能把越权降到 9.9%，作者认为主要脆弱性在底层模型。Relinking [26]（HKUST，摘要级）：压缩器会把分散的无害片段拼成完整的恶意指令，而过滤器只检查压缩前的 prompt。
- 【外】[27]：summary prompt 已明确要求保留约束，每次压缩仍丢弃约束类别：GPT-5.3-Codex 平均丢 2.73/3 类，GPT-5.4 丢 1.76，Claude Opus 4.6 丢 0.51。【外】[28]：收件箱实验中，压缩后 30/100 个会话未经批准删除邮件，压缩前为 0。【外】Governance Decay [29]、Compaction Cliff [30]（Sonnet 4.6 上 /compact 一轮保留 53% 安全规则，五轮后 10%）、ARCBench [31]、Reclaim [32]、Compaction Laundering [33] 给出同类现象。

**已有处理。** 约束 pinning [29]、SJC 后处理 [24]、来源感知提示 [25]、按类型分流保留 [30]。

**剩余问题。** 诊断已饱和，修法多是外部 pinning 或后处理。压缩器为何在指令明确时仍丢约束，没有机制分析；训练式 compaction（Q001）对来源保真度是放大还是减弱，本轮未见测量。**拥挤风险高**，若推进，应从训练侧或机制侧切入，不要再做一个诊断 benchmark。

### Q006 成功率与 token 数掩盖压缩代价

**实验发现。**
- [34]（UPenn/Oracle；7 个 LLM，1,514 个长程数据 agent 任务）：compaction 按任务平均对准确率的影响至多 2 分，但在所有 agent 组都增加重复动作；最强模型组上，所有上下文工程技术都不提升甚至降低准确率，成本还更高。
- [35]（Harvard；两家公司的生产 trace，14 种算法）：在 agent 前缀缓存上，复杂替换策略相对 LRU 收益很小，因为活跃会话节奏规律，近因极具预测力。DeepSeek-V4.1-Flash [36] 把"agent 工具调用造成 KV 未命中时的 prefill"列为架构设计动机。
- 【外】[27] 的论证：benchmark 有固定目标、运行时无用户输入、有持久文件系统，被丢内容可以靠重读自身产物找回；真实会话中大量上下文是只存在于对话里的用户指令。【外】[37]：在 SWE-bench Verified 上跑 9,400 次，整轮删除比删 75% token 损失更多任务和回合。【外】[38]：工具输出 token 减少 38.4%，计费反升 6.8%，token 削减与成本削减的相关系数 r=0.15，原因指向缓存创建。【外】Compact-Bench [39]：14 个 summarizer 后端的稳定损伤从 5% 到 64% 不等，与 [27]"benchmark 压缩友好"形成待解释分歧：前者用配对续写隔离单次替换的影响，后者看端到端成功率。

**已有处理。** 不压缩已压缩内容（【外】CliffCompaction [41]），异步或并行压缩（CoMem [42]），会话即可执行环境（Scroll [43]），压缩时卸载到外部记忆（ACM [44]）。

**缺口。** 缺少按"被丢信息能否从环境恢复"分层的评测；缓存感知的压缩点选择没有系统比较；白名单内对计费口径的受控证据少。**拥挤风险中高**（Compact-Bench、[40] 约 35,000 次运行等评测类工作已出现）。

### Q007 KV 级驱逐与文本级 compaction 没在同一 agent 预算下比较

覆盖扫描（129 篇正文，关键词级）：7 篇 agent 专用 KV 方法（IntentKV [47]、AgentKV [12]、StepKV [46]、CommitKV [45]、ActKV、MemDecay、[48]）都未命中文本摘要/compaction 基线；抽查 StepKV，LLMLingua 只出现在相关工作中。反过来，文本 compaction 方法也几乎不和 KV 驱逐对比。两列同时命中的 7 篇中，抽查的 2610.41291 只在相关工作提及 H2O/SnapKV；【外】[49] 在 AppWorld 上比较了 FIFO 与 ACON 摘要（表 2 首组：无压缩 44.0、FIFO 34.5、ACON 26.2，作者归因于摘要丢了执行标识符），但实验中没有 KV 驱逐。

**反证检索。** 做了一次网页定向检索。最近邻是 Still [50]：KV compaction 与自然语言摘要基线同表比较，但用的是 HELMET/LongBench 长上下文 QA，不是 agent。另一篇是【外】[15]：agent 场景，但只比较 KV 两族。结论：本轮范围内未检出多轮 agent 任务上的同预算跨层比较。这是评测覆盖缺口，**不等于已证明某一方失败**。

**为什么值得看。** 两层的失败类型可能互补。KV 驱逐不改写，不会写入无来源内容（避开 Q005），但依赖 query 代理（Q002），且绑定模型。文本 compaction 可读、可跨模型，但会改写、丢标识符、打断缓存（Q006）。对齐"同一预算"本身就需要先定义成本口径。

## 问题卡摘要与推荐顺序

推荐顺序按"问题值不值得做"排列（失败是否重要、机制是否未定、现有修法是否只治症状），不按实验难易。

1. **Q001 带压缩训练学到了什么。**（2026-11-04 打磨未过、已停止，见 Q001 打磨记录） 带压缩 RL 已成为长程 agent 训练的主流配置，但现有证据显示增益可能主要来自执行器适应、并伴随单窗口能力下降，而 RL 在无冷启动时会主动回避压缩。机制没人拆开，现有方法都是"加组件"式修法。算力：最小验证可用 8B 级模型 + 小规模 agent RL（Memento 规模），8×A100 五天内可行。
2. **Q002 查询未知时保留什么。** 这是所有压缩方法（文本与 KV）共同的上限问题，多个独立设置一致显示"为当前问题选择 ≈ 对未来随机"；现有修法（延迟压缩、阶段 query、依赖图）各自只治一种代理失效。
3. **Q003 潜在/KV 压缩为何在多步 agent 失败。** 负面结果明确（解决数低于基座），机制只有两个未检验的假设，且与"保真度不预测可消费性"的独立发现相呼应。拥挤度低。
4. **Q004 何时压缩。** 有一项扎实的配对重放结果给出可预测性上限，而学习式方法不断发表却没和这个上限对照；与 Q001/Q002 强相关，适合作为它们的子问题。
5. **Q007 KV 级 vs 文本级同预算比较缺失。** 已做反证检索的领域盲区候选；价值在于两层失败类型互补，但属评测缺口，单独做容易被视为审计类工作。
6. **Q006 成功率与 token 掩盖代价。** 重要但评测类拥挤，强证据多在白名单外。
7. **Q005 摘要混入无来源推理与丢约束。** 现象最清楚，但窗口内诊断已饱和；只有从训练侧或机制侧切入才有空间。

所有卡均无用户已有 idea。按项目记忆，审计/诊断类切口拥挤（idea-loop-lessons-20261103），Q005、Q006 尤其如此。

## 术语表

| 术语 | 说明 |
| --- | --- |
| Context compaction（上下文压实） | agent 上下文接近上限时调用 LLM 把历史改写成摘要，再从摘要续行；Claude Code /compact、OpenCode、OpenClaw 等 harness 的默认机制。易混：KV 驱逐不改写文本。 |
| KV cache eviction（KV 缓存驱逐） | 在模型内部删除部分 token 的 key/value，以注意力分数等打分；H2O、SnapKV 为代表。依赖"代理 query"估计未来注意力。 |
| Proxy query（代理查询） | KV 驱逐中用来估计未来注意力的 query，常取最近 token；agent 场景中阶段切换使其失效 [12][15]。 |
| Retention vs. Retrieval（保留与检索） | 保留是查询前决定留下什么，检索是查询后选什么送给模型；保留封顶检索 [10]。 |
| Pre-query retention（查询前保留） | 写入时不知道未来问题的保留设定 [11]。 |
| ICAE（In-Context Autoencoder） | 把上下文编码为少量连续嵌入的隐式压缩方法 [16]。 |
| Tolerable set（可容忍集） | 冻结读者能正确使用的 cache 区域；几何接近不等于在集内 [17]。 |
| Paired replay（配对重放） | 同一边界分别用完整历史和 summary 从同一环境状态续行，比较后续行为 [20]。 |
| Time-travel leakage | 带压缩训练时沿最终压缩路径计算损失，使后发生的驱逐影响之前 token 的条件分布 [4]。 |
| Unsupported entry（无来源条目） | summary 中既无环境输出也无上一 summary 支撑的内容，多为压缩器写入的决策和待办 [24]。 |
| Authority collapse（权限坍塌） | 记忆整合保留了陈述却抹去其使用约束，使其看起来比来源更有权威 [25]。 |
| Prefix caching（前缀缓存） | 服务端复用相同前缀的 KV，按缓存价计费；改写历史会使其失效 [35][38]。 |
