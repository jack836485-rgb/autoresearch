# 低显卡 LLM Agent 研究地图：从具体失败模式寻找切口

检索日：2026-10-10。近期窗口：2026-04-10—2026-10-10。独立目录：`path-stage/低显卡Agent失败模式_20261010/`。

你的条件是可用付费 LLM API、优先不训练模型、暂时不限定 agent 类型。因此，本地图聚焦冻结执行模型，研究工具使用、执行状态、用户交互与外部经验。模型推理可以交给 API，本地主要运行 CPU 环境；“不吃本地显卡”与“API 成本低”是两回事。

**优先从 Q001 开始：工具输出格式正常但内容错误时，agent 如何发现并恢复。** 它有公开的受控工具模拟，方便把错误识别、恢复动作和成本分开。第二选择 Q003：压缩评价遗漏不报错的状态错误。第三选择 Q002：获得澄清回答后仍遗漏旧约束。Q004 与 Q005 也有依据，但轮次、重放和归因成本更高。

这是一份有原文依据的问题地图。切口是待查新的研究假设；本轮没有确认任何算法为首次提出，也没有运行收费实验。

## 3. Q001：工具返回正常，但内容错误，agent 如何发现并恢复？

普通工具调用 agent 常把“没有异常、返回结构合法”当作可以继续的证据。ToolMaze 将任务拓扑与四类故障分开：显式／隐式 × 暂时／永久。原作使用 400 个基础任务，扩展为 2,000 个无扰动／扰动实例。在故障提醒条件下，Claude Sonnet 4.6 的显式暂时故障恢复率为 **90.61%**，隐式暂时故障为 **29.99%**。[1，§4、表2](https://arxiv.org/html/2606.05806v1)

这里的 PRR 分母是**实际遇到故障的轨迹**，而且正确终止不可解任务也可能计恢复；它不是全任务完成率。原作已经给出 failure-aware prompt，因此“告诉模型工具可能失败”已是 baseline。

适合你的研究问题是：**在没有隐藏故障标签、额外工具调用有限时，能否从当前子任务约束与工具证据的矛盾，区分该重试、该换路径和该终止？** 这是本轮提出的可检验假设，不是已查新算法。失败识别和失败后的策略选择应分别观测，否则成功率上升可能只是多调用了模型。

建议阅读／对照入口是基础 function-calling agent、同模型的 failure-aware prompt，以及已有运行时干预方法 Sentry。Sentry 已包含检测、检索经验、修复与验证，不能把这些组件的组合本身当作新贡献。[8](https://arxiv.org/html/2610.02994v1)

SSA 的跨模型案例也说明，要求更多工具调用可能令模型发出空调用凑数。工具调用数量不能替代有效进展。[12，§2.2](https://arxiv.org/html/2606.17454v3)

**低资源理由：** ToolMaze 的工具是本地确定性模拟，官方代码直接支持 API actor。注意仓库还配置了 LLM judge，其调用要计入预算；“CPU 工具”并不等于整个评测免费。[代码入口](https://github.com/Zhudongsheng75/ToolMaze)

真正有价值的结果应同时说明：隐式错误下的任务成功、遇故障后的恢复、干净任务上的误干预损失，以及 actor／judge／额外验证的总成本。方法运行时不能读金标准 DAG 或注入器隐藏标记。

## 4. Q002：问到了正确答案，为什么仍然违反任务要求？

AppWorld-UL 的错误分析不只报告“没有提问”，还明确记录两种后续失败：**收到正确回答后遗漏此前要求；一次问多个问题，却把回答对应到错误问题。** 原作没有给这两类各自的发生比例，不能编造占比。[3，§6.7](https://arxiv.org/html/2607.20536v1)

该基准有 516 个任务。最佳 Code Agent 的整体 I-TGC 为 48.6%，组合子集为 35.7%；I-TGC 同时要求终态测试通过与必要提问覆盖，不能称作单纯执行成功率。原作还发现，问得更多不一定更好。[3，§5–6](https://arxiv.org/html/2607.20536v1)

可检验切口是：**固定正确用户回答以后，分别比较答案绑定、旧新约束合并与续跑执行。** 例如用户明确了目标对象，agent 仍要保留原始任务对范围、条件和操作的限制。仅加入“有疑问就问用户”的提示不能证明解决了这个问题。

基础对照用原作 Code Agent 与 Function Calling Agent，并保持用户模拟模型、知识边界、任务状态和预算一致。隐藏知识集只供模拟用户和评测使用；把它直接给 agent 会移除研究问题。真人交互仍是独立验证边界。

**低资源理由：** 应用状态在 CPU 模拟环境中运行，actor 和用户模拟走 API 即可。与 Q001 相比，多了模拟用户、交互评测和组合约束的实现工作。[项目与代码入口](https://appworld.dev/appworld-ul/)

## 5. Q003：压缩评价会不会漏掉“动作合法、状态却错了”？

TRACE 从同一环境状态对比压缩前后闭环续跑，用动作被阻塞／报错以及重复取数衡量执行退化。其结论部分明确指出：**这类信号可能漏掉静默状态错误。** 这是一条作者明确写出的测量局限，原作未量化这种错误的比例。[4，§3.3、§7](https://arxiv.org/html/2608.06503v1)

需要保留条件差异：在 MiniMax-M3 的 168 任务、两次运行中，TRACE 平均成功率 77.1%，全上下文 85.7%；转移到 Kimi-K2.7-Code 时，TRACE 84.5%，全上下文 82.7%。不能写成“压缩必然损害 agent”。[4，表1–2](https://arxiv.org/html/2608.06503v1)

Microsoft 的酒店报销实验也有相反条件：固定 user model 时，全历史、最近五对工具交互、剪枝加摘要的完成率依次为 71.0%、79.0%、91.6%，每轮 benchmark 总 token 依次为 1,480,996、535,274、553,374；来自 50 任务、五次运行。它与 TRACE 的任务、模型和压缩方式不同，不是同设置矛盾。[5，§3–4](https://arxiv.org/html/2606.10209v1)

因此更具体的切口是：**摘要保留的信息是否还正确关联到实体、操作和确认状态？** 比如“调用成功”与“目标对象已达到要求”可能在压缩后被合并，后续动作合法却做错事情。应从相同压缩边界继续执行，检查实体匹配、约束满足和终态变化，判断它们是否补足 blocked／refetch 信号。

ARC 已有原始工具观察归档、ID 引用与回取。因此仅增加“保留原文、需要时检索”不是空白；其主要召回测试也不能自动证明动态执行状态正确。[6](https://arxiv.org/html/2607.25066v1)

**低资源理由：** TRACE 不更新模型权重，压缩器／actor 可通过 API 实现。原作公开了冻结边界数据，可先分析已保存轨迹；真正比较新方法仍需候选摘要、配对续跑与端到端验证，成本应包含这些步骤。[代码入口](https://github.com/nokia-applied-research/Trace)

## 6. Q004：该屏蔽一次经验，还是把它永久淘汰？

ReasoningBank 的附录 E 说明检索／整合采用简单方案，判断成功失败依赖 LLM judge。这些是作者声明的设计与信号边界，不能单凭该段断言它发生严重负迁移。[7](https://arxiv.org/html/2509.25140v2)

Sentry 已有更直接的受控证据：相同冻结经验库、相同按失败检索与修复机制，仅额外将完整库常驻上下文，WebShop reward 从 0.364 降到 0.296，Mind2Web Replay completion 从 0.651 降到 0.599。实验为 50 构建任务、50 不重叠测试任务、五次运行；两种指标不能合并成统一准确率。[8，表4](https://arxiv.org/html/2610.02994v1)

Ratchet 进一步已有按贡献淘汰、库容量约束与评审误判分析；新版还包含跨模型与初步 SWE 验证。它明确指出，router 选择会混杂贡献估计，因果解释需随机切换经验；经验演化反过来诱导 judge 盲点的情形不在其外生误判通道结果内。[9，§5.2、§7](https://arxiv.org/html/2605.22148v3)

值得继续区分的是：**某经验整体无价值，还是只在当前状态不适用？** 匹配状态下切换经验暴露，可以观察收益是否改变符号。Sentry 已覆盖条件暴露，Ratchet 已覆盖淘汰；只有证实现有机制未处理的条件，再提出改进才有意义。

**资源判断：** 不需要训练 actor，但经验生成、judge、重复暴露与长期轮次较多，API 费容易积累。它适合作为备选，不建议在没有明确失败复现时先构建庞大记忆系统。

## 7. Q005：诊断原因对了，为什么修复仍失败？

PROBE 在 257 个首次失败案例中，诊断匹配 168 个，修复 56 个。更有辨识度的是类别差异：工具异常类只修复 **3/47**；状态／工作流类诊断匹配 **35/42**，修复 **6/42**。[2，表3](https://arxiv.org/html/2605.08717v2)

这不是全任务成功率，也不能把聚合诊断率与修复率相除，得到“正确诊断后的修复概率”：原文没有所需交叉表。比较固定 actor、工具、评测及一次 repair 预算，反馈模型在 PROBE 与通用总结 baseline 中也保持一致。作者说明，一次修复是评测协议，而非框架只能修一次。

TrajDebug 已有关键错误定位、oracle 已知失败条件下的同任务修复，以及 held-out 失败经验转移。因而“定位根因后重试”或“将诊断写入记忆”已有工作；人工关键错误标签也不自动构成干预验证过的因果真值。[11，§6](https://arxiv.org/html/2608.06346v1)

False Success 研究还表明，agent 的完成宣称不能替代环境状态。已有轻量检测器可用于分流，但跨域需要校准，检测效果也不是修复效果。[10](https://arxiv.org/html/2606.09863v1)

可检验切口是：**在匹配失败起点和总恢复预算下，区分诊断错误、指导不可执行、状态不能修、环境阻塞与预算不足。** 若最终失败标签在现实中不可见，触发恢复时不能偷用 evaluator。优先在轻量工具任务验证，再考虑软件修复和微服务环境。

## 8. 如何按你的资源选

| 优先次序 | 基础环境／对照入口 | 不需要本地显卡的实现方式 | 最先要证实什么 |
| --- | --- | --- | --- |
| 1：Q001 | ToolMaze；普通与 failure-aware 工具调用；相关运行时修复 | CPU 工具模拟＋API actor／judge | 隐式错误收益来自识别或正确换路，而非更多调用 |
| 2：Q003 | TRACE、全上下文、相同预算的摘要；ARC 作为回取相关对照 | API 压缩器＋CPU 状态环境 | 存在 blocked／重复信号漏掉且影响终态的状态错误 |
| 3：Q002 | AppWorld-UL Code／Function Calling Agent | CPU 应用模拟＋actor／用户 API | 给出同样正确回答后，约束合并仍是独立瓶颈 |
| 备选：Q004 | ReasoningBank、Sentry、Ratchet | 外部文本经验库＋API | 局部不适用与全局有害能被实验区分 |
| 备选：Q005 | PROBE、TrajDebug；从轻量任务开始 | 轨迹离线分析＋API 反馈与重放 | 正确诊断不足以恢复的原因，能被单项干预分离 |

本地 GPU 为零的前提是把所有大模型推理交给 API；若自行部署原作大模型，资源口径会改变。CPU、内存、环境安装、工具调用和人工标注也要计入。ToolMaze 原作最多 25 步、16,000 生成 token 上限并不意味着每个实例都便宜。

本轮不预设你的实验模型、温度、步数、样本量或 API 金额。正式实验前需确定这些参数。比较不同方法时保持核心参数一致；actor、检测器、压缩器、用户模拟、记忆构建／选择及所有重试分别记账，不能只比较 actor 的单次 token。

## 9. 术语表

| 中文／英文 | 本地图中的作用 | 易混点 |
| --- | --- | --- |
| 执行模型／actor | 规划并发起工具调用的冻结 LLM | 外部经验更新不等于更新模型权重 |
| 执行框架／harness | 工具、上下文、状态和执行循环 | 换整个框架不能只归因于提示 |
| 隐式语义失败／implicit semantic failure | 输出结构正常但内容错误 | 格式校验不能证明语义正确 |
| 任务成功率／TSR | 所有评测任务的完成情况 | 与遇故障子集上的 PRR 分母不同 |
| 扰动恢复率／PRR | 遇到故障后的有效恢复 | 正确终止不可解任务也可能计恢复 |
| 交互任务完成／I-TGC | 终态测试通过且必要提问覆盖 | 不是单纯终态 TGC |
| 场景完成／I-SGC | 同一场景各变体均通过交互评测 | 比单任务指标严格 |
| 两次都成功／Pass² | 两次运行均解出 | 与至少一次成功的 Pass@2 不同 |
| 上下文压缩／compaction | 用摘要或缩减表示替换历史 | 存着事实不保证继续执行时会正确使用 |
| 假成功／false success | 宣称完成但独立状态检查未达标 | 文本自信不等于任务完成 |
| 关键错误／critical error | 被标注为对最终失败负责的步骤 | 事后标签不等于在线可识别或因果真值 |
| 负迁移／negative transfer | 经验引入后表现下降 | 需要匹配对照，不能仅看低成功率 |

## 11. 覆盖、阅读与交接边界

- **实际阅读。** 核心问题的证据覆盖方法、实验设置、表格、失败分析和局限。SSA 只精读 §2 的接口／提示案例，不声称精读其完整 124 页。ARC 只引用机制与验证范围，不使用其摘要汇总成绩。全文抽取与版本保存在 `资料/`。
- **检索并非穷尽。** 按八家主要机构与工具失败、记忆、压缩、交互、归因、评测词组查询。部分搜索忽略日期或返回旧作，均回原文核日期；没有完整遍历每家研究列表、月份和分页。阿里／字节的本轮候选未成为核心问题证据，不能解释为它们没有相关研究。
- **未使用的候选。** AutoCompact 涉及 SFT＋RL，不适合作为你当前“优先不训练”的起点；内部记忆电路研究需要模型激活，不直接适用于黑盒 API。若需要训练对照，它们可以后续按资源再评估。它们不计入主报告 13 项引用。
- **访问限制。** Beyond the Leaderboard 的 arXiv HTML 入口 404，未用于正式结论；AppWorld-UL 更早 OpenReview 日期因页面验证与 API 访问限制未核实，不计近期合格数。未为这些访问失败补造内容。
- **源码与论文差异。** ToolMaze 论文使用 270 工具，当前仓库 README 写 273 plugins；它们可能对应不同源码状态，本轮未运行确认，复现时需固定数据及代码版本。AppWorld-UL §6.1 的 Claude effort 描述出现 4.5，而成绩使用 4.7；本报告按表2解释成绩，具体配置须回源码核对。没有把不同版本数值拼接。
