# 电脑卡顿排查

排查时间：2026-10-29 10:38—10:42（北京时间）。

用户描述：整台电脑卡顿，包括鼠标移动或切换窗口。

## 主要发现

最值得怀疑的是一次 Windows DNS Client 服务的 CPU 高占用。首次性能快照中，服务进程 svchost.exe（PID 2220）约占总 CPU 的 44%，同期系统总 CPU 快照为 67%，其中内核占用约 54%。通过服务清单确认该 PID 仅承载 Dnscache。随后该进程占用恢复很低；对原始计数器做 6.6 秒差分，平均总 CPU 占用为 0.18%。

这与一次短暂的后台服务负载相符，但快照发生在开始排查后，没有卡顿当刻的连续记录，因此不能断定它就是全部原因，也不能确认触发程序。

系统存在 Clash、Tailscale、aTrust、OpenVPN、Cisco VPN 等相关后台进程。网卡状态显示 Tailscale 和 Oray 虚拟网卡启用，aTrust、OpenVPN 网卡未连接。它们的存在不等于发生冲突。DNS Client 的 Operational 日志未开启，无法从现有该日志追溯发起 DNS 请求的应用。hosts 文件仅 957 字节，没有文件过大的迹象。

另有 VS Code 的 Pylance 语言服务（Code.exe，PID 179288）持续使用约 4.16% 的总 CPU。在这台 24 逻辑处理器的机器上，相当于约一个逻辑核心的计算量。该进程私有提交内存约 2.2 GB，属于持续负载，但不足以单独解释整机严重卡顿。

## 建议

1. 如果再次出现同样的整机卡顿，优先观察任务管理器中 DNS Client 对应服务主机是否再次冲高。重复出现才能加强它与卡顿的关联。
2. 若卡顿与切换某个 VPN 或代理同步，保存工作后，仅退出当时不需要的那个客户端，观察同样操作是否仍触发卡顿。不要同时改变多个网络客户端。
3. 当前不使用的 VS Code 窗口可正常关闭，以释放持续运行的 Pylance 负载；不需要的浏览器和办公文档也可正常关闭。
4. 若仍持续整机卡顿，保存所有工作后重启是临时恢复手段。重启本身不能证明根因，也不需要先升级硬件。
